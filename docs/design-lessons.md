# 设计约束与验收要求

本项目保留知识谱系、规则语义、独立裁决和反馈治理，复用成熟的 Agent SDK、PostgreSQL 任务队列、检测引擎和对象存储接口。

## 领域边界

- EvidencePack 保存事实，ProblemCase 表达具体失败，RuleBundle 绑定风险语义、适用条件、例外、检测器和测试
- 静态匹配负责提名候选，独立语义判断确认适用性；缺少必要证据时返回 Unknown
- 规则版本、执行器版本、源 commit、配置、运行、Finding 和反馈必须可以关联
- 发布前核验授权、当前 commit、活动规则版本、位置和去重；候选生成器不直接发布
- 发布时有效性、开发者行为和当前代码状态分别保存；无回复不表示错误，resolved 不等于 fixed

## 执行边界

- 独立裁决使用独立会话，避免执行者的结论或其他案例污染上下文
- 外层分支、调用者、配置和取消传播可能使局部模式合法，不能只看一行代码
- 数据库队列并发不等于模型供应商 RPM/TPM；费用、任务重试和失效认证需分别处理
- 只读公共事实可以复用，可变文件和模型会话不能随意共享
- Worktree 提供文件组织，不构成安全沙箱；任意仓库代码不能取得发布或存储凭据
- 阶段输入超限应明确失败，不能静默截断后把不完整覆盖称为成功
- 成功阶段可以复用，失败尝试必须保留；新配置或新 attempt 建立新身份

## 评测口径

候选精确率、缺陷召回率和总体 accuracy 的分母不同。仅知道 TP/FP，不能推出 FN/TN。模型判决、人工判决、代码状态和混合反馈分别统计，不挑选较高比例作为系统准确率。

PR、Workflow、Evaluation、Rule、Finding、发布评论和 Feedback 是不同实体。同一 PR 可以既有有效发现也有误报；反馈必须绑定具体 Finding、规则版本和提交。

合成 fixture 只能证明机制，训练样例自己的 pre/post 回放只能证明回归行为。生产晋升需要独立标注案例和明确门槛。详见 [vLLM 实验](../experiments/vllm/RESULTS.md)与[验证范围](verification.md)。

## 运维边界

使用一个 k3s 集群不自动意味着高可用。PVC 声明容量也不总是硬配额。数据盘、WAL、镜像缓存、日志、临时工作区、认证状态和对象存储必须有各自容量、保留、备份与恢复策略。

默认流程不发布外部评论。真实仓库发布、完整上下文检索、隔离代码执行和线上持续演化均需独立集成验收；当前阶段详见 [README](../README.md)。
