# FlyReWheel Phase 0 抽样与标注协议

状态：待冻结的研究设计，2026-10-01。尚未建立正式抽样框、招募独立标注者或产生实证标签。本文的样本数、阈值和时间窗都是建议的事前决策，不能写成实验结果。冻结前须填全仓库名、抽样框清单、标注者与预算，并保存协议版本及哈希。

## 当前路线与本文的关系

2026-10-02 已选择先做[单仓库三时间窗实验](discriminating-experiment.md)：W0 从较早真实 PR 生成实验规则，在接触 W1 内容与标签前冻结；W1 对中期真实 PR 运行固定 reviewer，由独立人工核实实际 finding，形成明确标注来源的实验反馈；W2 在独立的较晚 PR 上比较冻结规则、自由更新、约束更新与有能力的 scoped memory，统一模型、证据、预算和 gate，分开报告人工提供与模型推断的 diagnosis。该路线尚未完成执行配置冻结或预注册，未产生新数据、模型结果或独立人工标签。

本文原有 3 仓库、90/180 PR、两时间窗与自然反馈调查保留为**暂缓执行的协议历史**，不再是当前实验的强制前置门槛。自然旧规则—反馈—更新链可以作为独立的补充 cohort，但找不到这类记录不阻止已选择的生成规则路线。下面的数值与继续阈值只属于原设计；不能将新路线的结果冒充这些条件已满足。原稿所说“只有两个前提成立才做效果实验”限定于该自然观察研究，不适用于当前受控实验。当前路线仍必须如实报告所有入框/抽中 PR、零机会与未知项，不能凭实验生成反馈推断自然复现率。

## 先回答什么

Phase 0 要确认：从历史变更抽取的仓库约束，在后续独立 PR 中是否有足够多可判断的使用机会；自然反馈中是否存在能够支持修正判断、补充适用边界或替换旧契约的证据。只有这两个前提成立，才值得投入诊断驱动更新的效果实验。

必须分别报告五件事，不能沿着这条链自动推导：

1. **复用机会**：历史时点可以提出的同一约束，在后续 PR 中再次相关。人工回溯建立关联，只能证明机会。
2. **实际复用**：当时的审查记录明确引用或可追踪地使用了旧规则、历史经验或先前修复。代码相似、同一 reviewer 出现，都不够。
3. **反馈后的代码修改**：反馈先出现，随后有对应代码变化，并有语义和归因证据。
4. **反馈后的规则修正**：旧规则或明确陈述的旧判断边界已经存在，反馈后其内容确实改变。修改代码、补测或研究者事后写出新版规则，都不自动满足这一项。
5. **反馈使后续审查更好**：需要独立未来案例上的受控对照。前四项的观察记录不识别这个因果效果。

本文将第 3、4 项最多称为“有文档支持的反馈关联修正”。即使作者明确说按建议修改，也无法排除其本来会独立作出相同修改。论文使用“feedback-caused correction”时必须说明这一识别边界。

## 研究总体与固定抽样

### 仓库层

正式样本选择 3 个公开、有完整 PR 记录的非 vLLM 仓库，至少覆盖 2 个应用领域、2 种主要语言。先依据研究可访问性和工作量建立候选仓库清单，再选仓库；不按已知规则成功案例、误报或契约变化选择。候选条件为：

- 在下列历史和目标时间窗中持续活跃，目标窗每月至少 20 个进入可审查状态的 PR
- 能取得精确代码对象及 review、评论、提交可见事件；无法取得的对象仍进入缺失率统计
- 至少有两名具备相关语言与领域经验的独立标注者；不要求他们是项目维护者

仓库选择是**目的性选择**，PR 层才做概率抽样。结论限于这 3 个登记仓库及其时间窗，不能称为开源软件总体的代表性估计。仓库名和候选清单当前未填，因此协议尚未预注册，也不能开始正式抽样。不能看完标签后替换“没有好案例”的仓库。

vLLM、现有 5 个种子修复、PR #8568 及其已研究的问题 lineage 全部属于开发集。可以用于训练标注者和修改 rubric，不进入正式样本或效果 holdout。若以后专门研究 vLLM，应另设未用于设计的时间窗和问题 lineage，并明确披露开发集接触。

### 时间窗与抽样单位

建议冻结以下 UTC 时间窗；更改必须在读取正式样本结果前登记新版本：

- 历史窗口 H：2025-10-01 00:00:00 至 2026-04-01 00:00:00，不含后端点
- 历史知识截止 C0：2026-04-01 00:00:00
- 目标窗口 T：2026-04-01 00:00:00 至 2026-07-01 00:00:00，不含后端点
- 事后标注观察截止 C1：2026-10-01 00:00:00，不含后端点

PR 的入框时间为首次非 draft、可供人审查的时间：非 draft 创建使用创建事件；draft 使用首次 ready-for-review 事件。不能用 merge 时间代替，也不能以后来是否合并、是否获得评论、是否修复 bug 决定入框。缺少可验证的 ready 事件时，保留该 PR 为时间不明；不能默认 createdAt 即可审查时间。无法分到月份的记录进入单独的 `frame_unknown` 清单，报告数量与原因，不伪造纳入概率。概率估计首先限于入框时间可确认的总体；frame_unknown 的覆盖缺口不在其置信区间内。若候选 PR 无法完整枚举或 frame_unknown 超过全部候选的 10%，先暂停正式抽样并修复 frame，不宣称仓库总体基率。

每仓库按月份分层，无放回抽取：

- H 每月 5 个 PR，共 30 个历史 PR，3 仓库共 90 个
- T 每月 20 个 PR，共 60 个目标 PR，3 仓库共 180 个

先冻结完整 frame，包括仓库、PR ID、入框事件、月层、是否 draft、可见性缺失和排除理由。由不读取结果标签的人一次生成并登记独立的 256-bit 随机种子，固定伪随机生成器实现/版本，在按 repository、PR ID 排序的每个层内做均匀无放回抽样。公布 seed、算法、抽中 ID 与完整清单，使选择可复现；不能试多个 seed 再选最好的一组。当前不生成 seed 或样本，以免把尚未登记的仓库方案伪装成已经冻结的随机实验。

每层记录 N、n 和纳入概率 n/N。若 H 某月不足 5 个，全部纳入并报告实际 n；T 不足 20 个属于仓库入框条件失败，应在查看结果前处理，不能用相邻月份补齐。抽中后因历史丢失或文件过大而无法判断的 PR 不替补，保留在原分母中。机器创建、未合并、无评论、纯重构、测试、配置和依赖变更均先保留；它们可能产出零规则或零相关实例。

3 个仓库、90/180 个 PR 是拟议 pilot 规模，不是功效计算或最终承诺。完整双人检查可能很昂贵：按下述目标 PR 上限，首轮最多 540 人时，统一补证轮最多再加 360 人时，尚不含 90 个历史 PR、培训和仲裁。先在开发集记录真实耗时并确认预算，再冻结规模；若资源不足，应事前减少仓库或 PR 数、放宽精度预期并明确定位探索性可行性研究。不能在正式标签出来后仅保留低成本或有阳性的 PR。

### 如何建立规则库

两名标注者分别只读 H 样本在 C0 前已可见的代码与讨论，提出有可检验证据的约束候选。候选至少写清：失败机制、约束、适用前提、已知例外、必要上下文、当时证据及未知部分。保留没有可抽取规则的 PR，报告其比例。

语法或语言普遍规律不自动算仓库专属规则。`repository_specific` 要求至少一个决定结论的前提来自本仓库的 API 契约、配置、架构、生命周期或特定产品语义；去掉这个前提，判断应发生变化或变成 unknown。通用空值检查可作对照，但不能填充仓库专属复用的分子。

仲裁者在未看 T 内容的条件下合并同一机制和约束的重复候选，冻结规则 family 与版本。一个 PR 可以支持多个不同 family；多个源 PR 也可支持同一 family。候选仅有评论声称、无足够代码或契约依据时，标为 provisional，不进入主分析的已支持规则库，但保留数量。冻结后不能为了匹配 T 中的案例重写最初规则，再称它是历史已知知识。

正式主分析针对“从这个有限 H 样本获得的已支持规则库”，不是所有历史知识。零机会不等于仓库从无可复用知识；必须同时报告历史 PR 数、可支持规则 family 数和覆盖范围。

### 如何找后续实例

两个标注者各自检查每个抽中的 T PR 及当时可见的相关仓库上下文，对**每个已冻结 family**记录 relevant、not_relevant 或 unknown。不能只验证检索器命中的候选。全文检索、静态模式或 embedding 可以导航，不能把未命中设为阴性。

先记录 PR × family 覆盖矩阵，再为 relevant 或 uncertain 的具体问题建立 instance 记录。同一 PR 中同一 failure mechanism 的重复位置聚合为一个 issue instance，保留全部 anchor；不同独立问题可有多条记录。PR 层机会率仍只计算一次。最初每个目标 PR 每名标注者上限 90 分钟，未完成部分标为 unknown；统一最多追加一轮 60 分钟补证，仍不足则保留 unknown。不要因看见好结果才无限补证。报告实际耗时及预算耗尽的比例。

允许额外检索跨 PR 链条以理解罕见例外，但必须标为 `enriched_case_study`，记录检索词和发现途径。其发现数不进入随机样本基率、门槛或首次重复间隔。额外搜索发现抽样矩阵中的漏标时，视为 rubric/覆盖问题，修订后统一重标相同层，而非只补正正例。

## 时间可见性与防止未来泄漏

### 三套彼此隔离的材料

1. **历史包 H**：规则生成者只能看 C0 前已可见的内容
2. **目标包 T(t)**：在某个目标 PR 的审查时点 t，含精确 base/head、当时 PR 描述和当时可以访问的仓库上下文；不含 t 之后的反馈和修复
3. **标签包 L**：独立标注者在完成第一轮 as-of 判断后，才可看 C1 前的后续讨论、修改和测试；它只能辅助事后判定，不能进入先前模型输入、规则生成或调参

主目标 checkpoint 使用首次可审查事件对应、且在第一条非作者实质性反馈之前已公开的 head。必须有可见事件把该 head 绑定到时点 t；commit authored/committed 时间不能证明它当时已经公开。若首次 head 无法重建，标 `unreconstructable`。可预先登记“最早可验证的审查前 checkpoint”作独立敏感性分析，但不能以最终 head 顶替主 checkpoint。

历史规则的 `available_at` 是支持该版本全部必要证据已公开的最晚时间。后续反馈的可见时刻也单独记录。只允许 `available_at < t` 的知识进入 T(t)；同秒且无可靠事件顺序时按不可用处理。反馈即使由较早提交触发，也只能在反馈真正发布后使用。

### 字段级限制

- 保存 `event_at`、内容版本的 `available_at`、API 抓取时间 `observed_at` 和可见性证据，三者不能混用
- 评论编辑后取得的正文不能回填到 createdAt。没有历史正文时，最早只能按可验证的编辑完成时间供后续使用；不能重建编辑前文字。只有当前 API 声称的时间，须记录信任层级，不能宣称独立证明
- pending review 在 submittedAt 前不对其他人可见。inline comment 的创建时间若早于 review 提交，使用两者较晚且可验证的公开时刻
- PR 描述、标题、labels、resolved 状态、重定向后的链接内容均可能变化；只有当前版本而无历史版本时，不得当成早期上下文
- 原始评论的 `originalCommitId` 与最终 `commitId` 分开。必须在其原始版本定位，不能把最终代码的行号和语义套回早期判断
- 目标的修复 diff、merge 结果、后加测试、后续问题描述、另一个案例的答案、未来 Git log 和当前默认分支不得提前暴露
- 不仅要隐藏文件：仓库对象库、refs、检索索引、缓存、共享 agent thread、路径中的标签和文件名均可能带入未来内容。回放使用当时可达对象的独立导出，记录允许对象清单；禁用在线访问和共享跨案例记忆
- 标注者后来看到答案不构成时间受控模型输入。若同一人先看过 T 或 C1 再写历史规则，该 family 标记污染并移出主分析；不得只靠让他“忽略答案”恢复资格

每个 checkpoint 保存 manifest：代码 SHA、来源 blob 内容哈希、base/head 选择依据、可见事件 ID、允许的讨论版本、拒绝提供的未来内容、缺失项及包哈希。哈希可检查内容一致性，不能证明历史真实性。无法重建时间顺序时应保留 unknown；数据不支持的 checkpoint 不能靠一个 schema 字段补出来。

公开历史可能已进入模型预训练。时间隔离不能消除这种污染。Phase 0 的人工观察结论与未来模型效果结论分开；后者必须披露模型版本和数据窗口，并考虑未公开或前瞻样本。

## 单位 独立性与排除

- **PR** 是抽样单位和机会率的主分母
- **Rule family** 是同一机制及约束的谱系；边界缩小、替代和退役是其版本关系
- **Instance** 是 family × 目标 PR × 独立问题，不是匹配次数或代码行数
- **Feedback episode** 是针对同一原判断/规则和同一问题的一组反馈及回应。一次 review 的多条回复不作多次成功修正
- **Lineage** 包含同一 bug 的修复、回滚、backport、cherry-pick、移植、复制代码和紧密关联 PR；family 相同本身不等于同一 bug lineage

计入“独立再次出现”须同时满足：不同于源 PR；原规则在目标 checkpoint 前可用；不属于同一修复 lineage；新的位置或新的变更场景要求重新判断；有独立证据支持机制与约束映射。语义相似或 AST 命中不够。仅改名、搬家、加注释、同一修复前后两侧、同一 PR 的下一次提交，均不是未来独立复用。

同一文件不自动证明同 lineage；不同文件也不自动独立。标注者先按 issue 引用、补丁关系、调用对象与变更意图核查，无法确定时标 `independence_unknown`。对相同源码 digest 的保守排除另报敏感性分析，不能把现有应用存储限制当成统计定义。

目标中原已存在、未被本 PR 改变且不可达性/契约也未改变的问题，标 `preexisting`，单独报告；主“PR 带来审查机会”分子仅含新引入、修改或因本 PR 的上下文变化而新近相关的实例。删除代码也可能改变不变量，不自动排除。生成文件、vendor、二进制或超预算对象的相关区域标 unsupported/unknown，不将整个 PR 移出分母或声明安全。

## 标注标签和证据要求

### 先判断适用性 再判断状态

每个 pair 分开记录：

- 相关性：`relevant / not_relevant / unknown`
- 当前规则状态：`violation / safe_applicable / legal_neighbor / contract_changed / unknown / not_applicable`
- 规则依赖：`repository_specific / generic / unknown`
- 变更归属：`introduced / modified / newly_relevant / preexisting / unknown`
- 上下文需求：`diff_sufficient / repository_context_required / external_context_required / unknown`

`safe_applicable` 是约束适用且被满足；`legal_neighbor` 是看似相似但前提不成立或有合法例外；`contract_changed` 要求早期契约确实成立、后来明确变化且影响本实例。不能仅因旧规则在当前报错就标契约变化。保留 as-of 判断与事后 judgment 两个字段；事后出现新证据可以更改标签，但不能伪装成当时可判断。

repository_context_required 需要指出决定结论的具体非 diff anchor。若要声称“diff-only 无法判断”，追加独立的分阶段试验：先锁定 diff-only 判断再解锁完整上下文；单凭标注者觉得有帮助只能称其报告的上下文需求。

### 开发者说法和审定标签分开

原始评论记录作者的来源身份、事件/版本、文字、引用对象和语言行为，例如提出问题、声称违规、声称安全、建议替代方案、确认采用、无法分类。它是 `source_statement`，不直接变成 TP/FP。

`APPROVED`、`CHANGES_REQUESTED`、`merged`、`resolved`、感谢、沉默、点赞、加测试或后续改了代码，都不是独立正确性标签。无评论不能当作没有 bug；有回复也不代表作者接受正确性诊断。记录“作者声称已修复”和“独立审定修复成立”时使用两个字段。

独立审定至少要有与该版本绑定的代码和机制说明，并满足以下任一支持路线：

1. 可复现的失败/修复测试，保存输入、环境、输出与版本；测试必须真正区分所声称机制，编译成功或 CI 绿色不够
2. 精确契约或完整调用链的人工论证，标明关键前提与适用边界；两位标注者独立判断后仲裁

两条路线分别报告，不把人工审定写成可执行 ground truth。运行不了测试不代表错误，证据不足则 unknown；相互矛盾且无法解决则 disputed。模型评分可以辅助找证据，不能充当第二位独立人类标注者。

### 反馈修正的分级

每个 episode 分开编码 `correction_target` 与 `attribution_level`：

- target：`code / finding / rule_boundary / rule_contract / tests_only / none / unknown`
- attribution：`no_observed_change / temporal_only / explicit_attribution / unknown`

“有文档支持的反馈关联修正”要求全部满足：

1. 有精确的旧代码/原 finding/原规则，并能证明它先于反馈存在
2. 反馈针对其具体机制或适用边界；泛泛的“looks good”不够
3. 反馈在相关改动首次公开前已公开，且次序可验证
4. 有精确改后版本，改动确实对应反馈的实质要求
5. 回复、引用或提交说明明确把修改归因于该反馈；只有时间相邻归入 temporal_only
6. 独立审定确认修改修正了相应错误或错误边界；相关契约仍不确定时保留 unknown

将同一 episode 的竞争解释一并保留：作者已在反馈前写好补丁、并行 reviewer 提出同一建议、独立重构、需求变化、只为结束讨论而妥协。证据无法排除时不把它写成“反馈导致正确性提升”。

针对 rule_boundary/rule_contract，还须提供实际旧规则和新规则文本或明确的审查原则变更证据。若从未存在显式规则，研究者可以标 `would_require_boundary_update`，但它只是候选诊断任务，不能计入“实际规则修正”。代码反馈丰富而实际规则修正稀少时，H2 的自然历史证据仍然薄弱。

最后记录是否在修正之后、C1 之前存在**独立的后续实例**。没有后续实例是 right-censored/unobserved，不是修正成功或没有回归。定向找到的未来实例可进入案例研究，不能混入抽样目标的机会率。

## 独立标注和仲裁流程

1. 在开发集上培训两名标注者和一名仲裁者，讨论最多 12 个训练 units。培训材料和最终 rubric 冻结；这些 units 不进入正式一致性或结果
2. 历史规则组只看 H；两个标注者分别提交规则与证据，仲裁冻结 family。规则作者不担任该 family 未来实例的最终仲裁者
3. 目标标注第一轮只看 T(t) 和冻结规则，彼此不可见判断，不看自然反馈、后续修复、FlyReWheel/baseline 输出或方法名称
4. 锁定第一轮记录和耗时后，第二轮解锁 L，分别标注 developer statement、反馈归因和事后语义状态。保留每次改判理由，不覆盖第一轮
5. 全部主样本双人独立标注。第三人只在两份原始判断锁定后仲裁分歧及全部拟计入“实际复用”“规则修正”“契约变化”的阳性，不因需要凑数强迫达成二元标签
6. 无法裁决记 disputed；补证后形成新标签版本，记录 supersedes。任何规则内容、时间可见性或 family 归并修改均须重新检查全部受影响 pair

报告仲裁前各字段的原始一致率、混淆矩阵、类别样本量和 Cohen's kappa，并给出适当区间；极低基率下 kappa 不稳定，不能只报一个数。另报 unknown/disputed 的比例及分歧原因。只有一个实际标注者时，输出应称“单人可行性试标”，不能声称独立验证。人员不足是数据生产阻塞，不应用多次模型自评掩盖。

## 主要报告量与不确定性

所有数量先给每仓库、每月和原始计数，再给汇总。主分析仅用按协议抽中的 PR、冻结的已支持仓库专属规则及独立审定结果。开发集、synthetic、定向补样、generic 与 provisional 分开报告。

1. **目标 PR 机会率**：至少有一条独立且 introduced/modified/newly_relevant 的已确认相关实例的目标 PR / 全部抽中目标 PR。分别给 violation、safe_applicable、legal_neighbor、contract_changed 的 PR 比例；类别可重叠
2. **规则复现覆盖**：至少在一个独立目标 PR 中再相关的 family / 冻结 family；同时给每条 family 的独立 PR 数。一次复现与两次以上复现分别报告
3. **间隔**：原规则 available_at 到首次抽样观察到的相关 PR 的天数和 PR 顺序间隔。由于只抽取 T 的一部分，必须写“首次抽样观察”，不得称真实首次复现或直接做完整生存分析。无观察报告窗口与右删失
4. **实际复用记录**：有当时显式使用证据的独立 PR 数、family 数、覆盖仓库数；其余机会记录 actual_use_unknown，不能据沉默推断没有使用
5. **反馈构成**：抽中目标 PR 内全部实质性人类 feedback episodes 的数量和类型；bot/行政消息单列。分别给代码修正、finding 修正、真实规则修正、纯补测、仅时间关联、不可判定的分子和分母。回复条数不能作为 episode 分母
6. **更新机会**：经审定 would_require_boundary_update / contract_changed 等诊断任务数及实际修正规则的数量，两者分开；再给后续独立可评价实例数
7. **可测量性**：checkpoint 可重建率、source 版本可追踪率、证据类型、缺失/unknown/disputed、时间与算力成本。逐项列出缺失原因

PR 层采用月层权重 N/n，估计登记 frame 内的比例；同时保留未加权计数。规则层结论条件于已抽到的历史库，不能把大量 rule × PR pair 当独立样本来缩窄区间。主 PR 比例报告 95% 区间，按仓库/月层内重采样整个 PR，保留其全部 instances；冻结 10,000 次设计一致的分层 survey bootstrap 及其种子，并处理无放回抽样的有限总体修正，n=N 的层无抽样变异。不能直接对所有 instance 做普通 IID bootstrap。该区间只覆盖目标 PR 抽样变异，不覆盖仓库目的性选择、有限历史库或标注系统误差。3 个仓库不足以支持一般总体的精确仓库级推断，不报告虚假的“跨仓库显著性”。

零阳性或极少阳性的层不能用退化的 bootstrap 得出零上界。对此事前固定有限总体超几何反演的保守区间；可将 Bonferroni 校正后的各月层区间按总体权重聚合，作为稀疏样本的同时保守界。实际采用的区间实现和边界单元测试应在分析脚本中冻结，不能事后挑最有利的方法。

同时给可判断样本条件比例和全样本保守边界。设确认阳性 PR 权重和为 C，尚无确认阳性但仍可能为阳性的 unknown/disputed/unreconstructable PR 权重和为 U，总 PR 权重为 W，则全样本机会比例范围为 [C/W, (C+U)/W]，C 与 U 不重叠。这是未决标签的识别区间，不是 95% 置信区间；对两端另报抽样不确定性。unknown 不能一律扔掉或按安全计零。已确认不相关才进入明确阴性；包缺失等 operational exclusion 仍保留在 U 中。重复 lineage 不进入独立阳性，但另报其数量。

Phase 0 不报告系统 precision/recall、反馈收益或业务 ROI。它还没有穷尽所有缺陷的 oracle，也没有运行匹配 reviewer 对照。

## 继续 缩小或停止的事前门槛

以下是决定是否投入下一阶段的实用阈值，不是对自然现象的普遍定律，也不是按统计功效推导的样本量。正式抽样前须由项目接受成本门槛；修改阈值要登记并将后续分析标 exploratory。固定这轮样本后，不得一直补样直到跨过门槛。

### 可测量性门槛

若不可重建/unknown/disputed 的目标 PR 超过 20%，或核心 relevant/state 字段仲裁前原始一致率低于 80%，暂停效果实验，先修数据协议或缩小可测子领域。不得删除这些 PR 来通过门槛。若单个类别少于 10 例，不对该类别的一致性或比例作稳定结论。阈值通过也不意味着标签无误，仍须公开完整不确定性。

### 规则复用门槛

进入 H1 原型效果实验至少要求：在正式概率样本中，20 个独立目标 PR 有确认的仓库专属机会；覆盖至少 8 个 family 和 2 个仓库；其中至少 5 个 PR 是已审定 violation，至少 5 个 PR 是 legal_neighbor。这个门槛要求同时有检出与误报风险，避免只靠大量安全适用代码撑起机会率。

若机会率的乐观标签上界的 95% 抽样上限仍低于 10%，则在登记范围内停止广泛持续复用叙事。若机会集中在一仓库、一组件或一种机制，缩小论文问题并用新样本确认。若不确定性区间跨过 10% 而计数不足，结论是“不确定/样本不足”，不能宣称机会不存在，也不能宣称可行性已被证明。

### 诊断更新门槛

进入 H2 对照实验至少要求：8 个经审定的边界或契约更新机会，覆盖至少 4 个 family、2 个仓库；其中至少 4 个 episode 在反馈之后有独立、时间可重建的后续实例可用于检验。这些门槛中的机会和后续实例均须落在正式概率样本内；C1 前定向补找的实例只能作案例研究，不能帮助跨过门槛。若要把“契约演化”作为核心主张，至少需 3 个独立 contract_changed episodes，来自至少 2 个 family。它们是下一阶段最低开发规模，不构成充分功效。

此外分别检查实际记录：若没有至少 3 个具备前后规则证据及 explicit_attribution 的真实规则修正 episode，则不得声称已在自然历史中建立“反馈驱动规则修正普遍存在”。可以继续做受控方法研究，但定位应改为“基于真实反例构造的规则维护任务”，明确规则更新是实验干预，而非观察到的人类行为。实际复用证据不足时，也只主张复用机会。

若主要反馈是测试要求、表达偏好、重复或未说明理由的拒绝，边界/契约任务很少，缩小或放弃诊断分类主线。若 H1 门槛通过但 H2 不通过，优先研究静态条件化迁移，去掉自我改进主张。若未知项太多，先改历史捕获或做前瞻 shadow 采集；不可把数据缺失包装成负结果。

## Phase 0 之后才做的因果检验

在上述门槛通过后另行冻结 Phase 1：将完全相同的旧规则状态、当前仓库、原始反馈与预算提供给冻结规则、反馈追加 memory、通用反思和诊断更新各 arm；更新后只在独立未来 PR 上评估。原始反馈与专家诊断标签分开，oracle arm 单独报告。对反馈本身的增量作用，增加无该反馈或移除目标反馈内容的对照；对诊断机制的作用，比较信息量一致的更新方法。

固定模型版本与调用配置，使用干净实例，随机化运行次序，必要时重复随机种子并报告方差。按 PR/family 做配对分析，联合报告新误报、漏报、旧有效案例保持、abstention 和维护成本。减少报错但丢失旧正确检出，或只是停用规则，不算有效修正。这个受控回放识别的是所设实验条件下更新操作的效果，不能自动推广为真实开发者行为的因果结论。
