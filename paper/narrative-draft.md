## 核心论点

FlyReWheel 可以研究这样一个问题：从历史变更中学到的仓库审查知识，怎样在新上下文和仓库演化中保持有效？

当前最值得验证的假设是：**在相同诊断、证据、预算和回归门禁下，强制限定规则可修改的字段，是否比自由更新和有能力的局部记忆维护更少重复误报，同时保留有效检出。** 判定错误、缺失上下文和边界错误分层报告；契约变化的有效性不纳入首个实验。

“历史 PR → 语义规则 → review → 反馈 → 规则更新”是方法链。真正需要解释和检验的是链上的知识有效性：什么时候可以迁移一次修复的经验，什么时候必须缩小范围，什么时候应该停止使用它。

工作标题可以是：*FlyReWheel: Maintaining the Validity of Repository-Specific Review Rules*。是否使用这个标题，要等实证结果能否支持“有效性维护”这一主张。

## 从一个可以观察的失败开始

下面是用于阐明研究问题的假设例子，不是已经运行的实验，也不代表某个真实 PR 的完整行为。

一个历史修复把分布式 worker 的直接方法调用改为 RPC。一个过度泛化的 reviewer 学到了“worker 调用必须使用 RPC”。它随后对本地 backend 中完全合法的直接调用反复报错。

这里至少有三种不同的问题，不能只用一个 thumbs-down 处理：

1. 判定错误：当前代码实际已经走了 RPC，reviewer 错看了调用链。需要修正本次 finding 或证据获取，不应为了消除一次误报而放宽规则。
2. 缺失例外：当前确实是直接调用，但它只在本地 backend 执行。需要补充适用条件或合法例外，分布式场景的约束仍然有效。
3. 契约变化：后来的统一 executor API 已负责本地与远程分派。旧规则可能需要替代或退役；继续在调用点强制 RPC 可能反而违反新架构。

历史修复提供的只是有上下文的证据。一次修复本身不能证明一个普遍规则。一个反馈事件同样不能直接证明整个规则无效。

论文第一步应在真实、按时间展开的审查记录中建立这类失败的存在与频率。若大部分反馈只是重复问题、表达偏好或信息不足，而边界和契约变化极少出现，这条研究主线的实际价值就会变弱。

## 研究对象与问题定义

研究对象是带版本的条件化语义规则，可以概括为：

R = 〈约束及原因，适用条件，合法例外，需要的上下文，来源证据，回归案例，版本关系〉。

规则的 scope 或静态模式只帮助找候选位置。语义适用性还可能依赖 backend、调用者约束、生命周期、运行配置及其他文件。判断至少应允许“违反”“安全”和“上下文不足”，不能把未覆盖自动视为安全。

一条 finding 还应绑定当前 PR 的精确版本、规则版本和支持判断的代码证据。规则迁移是否有效，要在后续独立变更上检验。

主研究问题：在只能访问当时已知代码、历史和反馈的条件下，显式诊断并更新规则的适用边界，是否优于保留同样历史与反馈的通用 reviewer memory？

## 方法链与需要讲清的机制

### 历史学习

从历史 PR 的修复、讨论和相关代码中提出规则候选，同时记录该约束依赖的条件和尚不确定的部分。正例与修复后代码为种子证据，不自动成为普遍适用性的证明。一个 PR 混有重构、功能变更和 bug fix 时，需要明确哪部分证据支持哪条约束。

### 当前审查

在绑定 commit 的完整仓库 workspace 中，让 review agent 自主探索调用链、配置、测试和契约。历史与当前版本要隔离，避免把一个版本的事实混入另一个版本。对审查中的目标 PR，只能提供当时可见的信息，不能提前暴露后来的人类修复。

静态扫描是可选的候选定位资产。全仓探索、多 commit workspace、Codex 和 OpenAI 工具都是方法实现的条件；除非实验单独证明对应算法收益，不应把工具名、部署方式或 self-host 能力列为科学贡献。

### 反馈诊断与规则更新

将反馈关联到原 finding、证据和精确规则版本，先判断是哪一种失败，再选择动作：

- 判定或证据错误：修正 finding，补足上下文或审查程序，原则上保留原语义约束
- 适用范围过宽或漏写例外：最小化修改条件或例外，并保留仍成立的正例
- 仓库契约发生变化：用有时间边界和来源的版本替代旧规则，或将旧规则退役
- 反馈只是低优先级、重复或未解释的拒绝：保留不确定性，不把它伪装成规则错误

候选修订在已经可用的回归集合上检查，再决定是否启用；保留版本与回滚依据。更新动作不能只依赖模型口头解释，必须以旧有效案例、新反例和未来独立案例的行为变化检验。

本轮实现并以 authored fixture 验证了这套设计中的结构约束：诊断声明限制可选算子，判定／上下文类结果不产生规则改写，边界修改保留语义核心，契约替代必须提交待审核的转换声明。混合、冲突或不足的证据触发弃权；具体门禁顺序见方法草案。尚未证明诊断正确、修改最小或有效，也没有执行 finding 修复、上下文获取、契约路由或退役。版本管理、provenance 或“闭环”本身不构成独立新颖性。

## 三项贡献候选

1. **问题与对象**：定义并实证分析仓库专属 review 知识的有效性问题，区分判定错误、适用边界错误与契约变化。若没有真实数据支持其重要性，单独增加 schema 字段不足以成立。
2. **方法**：提出反馈诊断驱动的选择性更新，并证明局部改写、替代和退役相对于同信息量的记忆追加或通用反思有独立价值。这个方法是最应投入的技术部分。
3. **评估协议与证据**：构建时间严格隔离的历史学习、反馈更新与未来审查回放，包含合法近邻、语义等价的不同实现和真实契约变化；同时衡量误报、漏报、保留能力与代价。

这些都是候选贡献，不能在获得证据之前写成已经完成的贡献或首创声明。

## 先确认知识复用与实验反馈的机会

已选择的三时间窗实验仍需测量复用机会；原 Phase 0 的自然反馈调查与数值门槛暂缓。先按固定抽样框保留真实仓库 PR 序列和零机会项，独立标注：历史经验是否在后续变更中再次相关；相关实例中有多少是真正违规、合法近邻或契约变化；这些信息是否需要 diff 之外的仓库上下文。不要只筛选已经知道“规则能起作用”的 PR。

报告机会基率、首次重复出现的间隔、每条规则的独立后续实例数，以及无法判断的比例。历史规则库规模不能代替复用机会；把同一修复的 before/after 当两个后续实例也不成立。标注后续结果可以服务于离线评价，但这些结果不能提前提供给模型。

如果在有代表性的序列中，相关知识几乎不再出现，或只有少数挑出的案例需要边界修订，应先缩小目标领域或放弃“持续有效性”的广泛叙事。这个检查是研究可行性门槛，不是预先保证主实验成功。

## 两个可证伪的主要假设

### H1 条件化规则能够正确迁移

这是保留的后续研究问题，不增加到当前 H2 pilot 的对照臂中。

在未来未见 PR 上，显式适用条件与例外能减少与历史修复相似但合法的代码上的误报，同时维持对真正违规的检出。

匹配的比较包括：同一模型和工具的无历史 reviewer、检索原始历史 PR 的 reviewer、只保存自然语言经验摘要的 reviewer，以及条件化但冻结不更新的规则。所有方法获得相同的当前仓库访问能力、历史截止时间和总成本约束；另报告各方法实际消耗。将生成与维护规则的成本计入，而不只比较最后一次审查的 token。

核心指标：经独立审定的 issue-level precision/recall、固定误报预算下的召回、合法近邻的误报率、unknown/abstention 比例、每 PR 的重复 finding 和成本。不能只报告 precision，因为完全不报问题也可能让表面指标变好。

消融：去掉适用条件、去掉例外、保留同等长度的普通总结。若条件化表达的收益来自更长 prompt 或额外人工整理，主张需要相应收缩。

### H2 强制更新约束是否有额外收益

主要机制对照是 H 与 U：两者得到相同的冻结诊断，H 强制执行可修改字段的限制，U 可自由修改规则。必需的实用 baseline 是有能力的局部增量记忆 M，可保留、修订、限定或抑制经验；F 保留初始规则。四臂使用相同的目标证据、reviewer、检索范围和资源上限，更新臂使用相同 gate 和一个提案名额，均不强迫改写。

人工提供的诊断 O 与模型推断的共享诊断 I 分开报告。I 仍依赖人工核实的实验反馈，不能称为自主从自然评论学习的端到端结果。去诊断或去 gate 只是另行冻结的补充消融，不能代替同诊断、同 gate 的主比较。

衡量独立 W2 PR 上的正例召回、合法近邻误报、严格负例解决率、漏报、覆盖丢失与总成本。被 gate 拒绝、保留、弃权或未完成上下文请求的 episode 仍用实际有效状态评估，不能从分母消失。若只获得边界错误案例，结论限于边界字段限制；缺失诊断类别或未来正负例要如实报告。

强反证包括：诊断错误导致有用修改被禁止；H 不优于 U 或 M；误报下降由漏报、路径排除或无依据的沉默换来。自然完整规则维护链不是本实验的前提，足够的真实复现与独立标签仍未建立。

## 实验必须排除的替代解释

- **看过答案**：训练、规则构建和调参仅使用 cutoff 前的信息。目标 PR 后来的修复与讨论只能用于事后标注，不能进入审查或提前的规则更新。
- **事件时间泄漏**：按实际可见时间处理 PR 与反馈，不能只按 commit 时间排序后把后来评论提前加入 memory。
- **相同案例复现**：种子 before/after 回放仅是机制检查。相同补丁、近重复修复、同一 bug 的关联 PR 应分组；需要未见位置与实现方式的后续案例。
- **仓库访问不公平**：不能给 FlyReWheel 全仓探索，却只给 baseline 一个 diff，再把差异归因于规则学习。diff-only 可以是单独的工程消融。
- **人工监督不公平**：各方法必须获得同一批原始反馈。人工诊断标签可以作为 oracle 上界，但不能把 oracle 分组当作端到端结果。
- **标签不完整**：没有评论、线程 resolved、PR merged 都不意味着没有缺陷或 finding 正确。独立审定应记录歧义；自然反馈与独立标签分别报告。
- **模型污染**：时间切分控制实验信息泄漏，无法保证公开历史从未进入预训练。应披露模型版本、数据日期和污染风险，优先补充模型知识截止后的新数据或前瞻 shadow 评估。
- **少报换精度**：联合看召回、false-alarm budget、abstention 与维护成本，不能用单个 useful ratio 代替全部目标。
- **只对单仓库成立**：若效果局限于一个领域或有丰富历史的大项目，应把结论限定到该范围。

## 与最接近工作的真实边界

### RhoSynth

RhoSynth 从带标签的代码例子合成逻辑形式的静态分析规则，并使用额外的误报例子进行规则细化。它明确使用开发者代码变更作为正负例来源。因此，“历史变更学习规则”和“用户反例驱动规则改进”均不能直接作为 FlyReWheel 的新颖性。

FlyReWheel 拟检验的差异是更依赖仓库上下文的语义 review，以及跨时间的边界和契约变化诊断；是否构成足够贡献，取决于具体算法与实证。

来源：[Example-based Synthesis of Static Analysis Rules](https://arxiv.org/abs/2204.08643)，2022-04-19；[原文](https://arxiv.org/html/2204.08643v1)。

### Archer

Archer 已将历史编译器 correctness fixes 提炼为 pass-level semantic obligations，让 agent 探索代码库，并使用可执行验证约束最终 finding。它比较了原始历史检索和全部历史上下文等替代方案。Discussion 也提出把失败案例反馈用于修订 obligations，并用回归案例检查。

因此，“历史修复 → 语义义务 → 全仓 agent review”高度重叠。FlyReWheel 不能把 Archer 描述成只有单次审查，也不能仅靠换到通用仓库宣称贡献。可尝试的差异是将跨时间的适用性、例外与契约失效诊断做成明确机制并独立评估。Archer 的可执行证据强度也是需要正视的参照；不具备同类 oracle 的场景必须明确标签如何获得。

来源：[Archer: Towards Agentic Review for Compiler Optimizations](https://arxiv.org/abs/2607.01808)，2026-07-02；[原文](https://arxiv.org/html/2607.01808v1)。

### AutoCommenter

AutoCommenter 学习并检查编码 best practices，并在部署中通过反馈进行调整。原文专门报告过时 best practices 导致误报，以及用条件化过滤抑制这类预测。它也指出已有审查评论并不构成完整 ground truth。

这些是有效性问题已有实际证据的支持，同时限制新颖性：动态抑制、反馈与 outdated-rule handling 本身都已有先例。FlyReWheel 必须解释更细粒度的诊断和更新为何值得增加复杂度。

来源：[AI-Assisted Assessment of Coding Practices in Modern Code Review](https://doi.org/10.1145/3664646.3665664)，AIware 2024；[作者原文](https://arxiv.org/html/2405.13565v1)。

### Learning to Commit

这篇 2026-03-27 的预印本通过历史提交上的监督式对比反思，累积仓库专属 skills，再用于未来 PR 生成，并采用时间切分评估。因此“历史提交 → 可复用仓库知识 → 后续任务”也已有近作。任务输出与 review 不同，但单纯将 memory 接到 reviewer 上仍不足以保证新颖性。

来源：[Learning to Commit: Generating Organic Pull Requests via Online Repository Memory](https://arxiv.org/abs/2603.26664)；[v1 原文](https://arxiv.org/html/2603.26664v1)。这里引用其方法重叠，不把预印本等同于已被会议接受的结论。

以上是四项有针对性的原文核对，不构成穷尽的新颖性检索，也不能据此作出“首次”声明。

## 当前代码可以支持到哪里

2026-10-02 最初对照源码 `e0e6c380d710434f4d0541b1a238784045130db8`；后续分别核对 `000c50d670ac2bbd007eca2bdecde0bf53093c84` 上的诊断算子扩展，以及 `92b375e62f141127214188a70b9024eec5ae7c27` 上的混合锚点工作区扩展。各轮验证范围独立记录。已有工作流包含：

- 语义规则 schema 中的 mechanism、invariant、applicability、exceptions、requiredContext、来源与版本关系
- 绑定规则和 change snapshot 的审查、证据 anchor、反馈记录与 revision request
- 静态候选扫描和 offline fixture 路径
- 受监督的 mining 与 semantic review workspace API，以及冻结反馈后的结构化修订提案、同快照对照和本地决策
- 显式编写的 SDK worker 输出驱动的单命令 fixture 闭环，包括保留一个正例、修正一个负例，以及拒绝丢失正例的候选

语义 review 已增加 workspace_execution 模式，但当前可接受的证据 anchor 和 coverage 仍限定为 changed-entries-only，repositoryContext 仍为 incomplete。全仓可访问不等于全仓证据已捕获。新 fixture schemaVersion 2 与 semantic-review-v2 worker 输出用 anchorJudgments 保存位置级判断，每个位置独立验证精确来源、证据和上下文缺口。同一文件可同时保留违规位置与合法例外；目标整体 unknown 不抹掉已有充分证据的局部判断，也不能反过来由局部判断推成文件安全。

当前 per-anchor-semantic-v3 比较器分别处理文件级案例与精确 TP/FP 锚点。它接受新 anchorJudgments 或旧版显式 findingAnchors，但全文件 safe、证据引用和零匹配都不能替代精确锚点的安全声明；缺失判断仍为 inconclusive，已声明扫描必须全部完成，删除正例也不会将其移出对照。新 receipt 用 per-anchor-v3 绑定 prompt/schema；旧 fixture、receipt、prompt 与评分报告按原契约重建，旧 accept 仍可读取，只有当前 scorer 的 compatible 对照可新增 accept。对应[验证记录](../docs/evidence/mixed-anchor-review-verification-2026-10-02.txt)和[compiled mocked SDK → worker → store → comparison 检查](../docs/evidence/compiled-mixed-anchor-review-smoke-2026-10-02.json)仅验证 authored fixture 下的实现行为，不涉及真实模型或后端，也不证明误报减少、召回保持或泛化收益。

修订生成仍使用 selected-evidence-no-tools。本轮新增 rule-revision-v2 和 diagnosis-operators-v1：判定诊断保留规则，上下文诊断请求上下文，边界诊断仅允许 applicability／exceptions／paths 发生实际修改；契约替代要求旧版本 digest、不同的旧／新契约文本、来源引用和待审核的适用范围声明。选择不确定或冲突、诊断混合时必须弃权；除上下文类外，声明缺失证据也必须弃权。所有来源和回归角色保持固定，无修改结果独立保存 receipt、diagnoses 和 nextStep，不制造新版本或修改 finding。旧 v1 记录按原 schema／prompt 读取，不追授新策略保证。

这些结构约束已通过本轮[实现验证](../docs/evidence/revision-operators-verification-2026-10-02.txt)和[compiled fixture 检查](../docs/evidence/compiled-revision-operators-smoke-2026-10-02.json)，不能证明诊断真实、边界逻辑收窄或最小、契约变化已发生，也不执行激活、路由或退役。所有诊断和模型输出均为预先编写的 fixture，验证只支持对应实现行为，不能据此宣称已验证原因感知算法或真实效果提升。

不可变 revision request 仍保持原来的 pending/not_run，而单独候选、无修改结果及收据记录生成执行；不能只看 request 状态就断言没有生成能力。既有闭环验证中 modelExecution 仍为 not_run，所有语义判断和 TP/FP 都是 fixture，人工 verdict 保持 Unknown，没有规则激活。现有工作区的 all-local-refs-v1 也不是时间隔离。它们支持工作流验收，不支持真实模型质量、独立未来泛化或反馈带来的效果主张。

检查依据和仍缺能力详见 [方法草案](method-draft.md)及[证据清单](claim-evidence-checklist.md)。实现仍在变化，正式写作前应对评测使用的固定 commit 再核对。

现有 `experiments/vllm/RESULTS.md` 明确将五组历史修复回放限定为种子样例回归：规则构建已经看过修复结果，语义状态是未独立验证，未运行原项目测试。这些材料可以说明为什么静态候选在修复后仍可能存在，不能作为未来检出率、语义判断准确率或自我改进的证据。

## 何时该收缩故事

如果匹配的原始历史与反馈 memory 已经一样有效，应报告负结果或将贡献收缩到数据与实证观察。

如果只发现条件化规则有效，而诊断更新不带来额外收益，可以写成仓库上下文约束的规则迁移研究，去掉自我改进主张。

如果主要进展仍是可复现的接入、追踪与工作流，则适合作为系统原型或工具工作继续积累证据。self-host、provider adapters 和 OpenAI 工具接入的工程价值不需要包装成算法新颖性。

下一步按已选择的 W0/W1/W2 路线准备单仓库抽样框、可见性与隔离记录，再冻结生成规则和实验反馈流程。当前可先做本地材料、模板和校验；新 PR 获取的 HTTP 403、真实模型认证执行和独立人工安排仍待解决。不得据此宣称已有 benchmark，也不自动授权登录、API 付费、上传或联系标注者。
